# API.md: REST API Specification

**Product:** Sales Call Quality Analysis Agent
**Source documents:** `PRD.md` v1.0, `ARCHITECTURE.md` v1.0, `DATABASE.md` v1.0 (source of truth); `DESIGN.md` consulted for UI-facing vocabulary
**Status:** Draft v1.0 (23 Nov 2026). Contract only. No application code.
**Examples:** Every payload in this document is **synthetic**. The call IDs, names, quotes and timestamps in section 17 come from the labelled synthetic seed data in DATABASE.md section 8. None is a real customer recording.

## 0. Reconciliation With the Source Documents

ARCHITECTURE.md 6.2 and 6.6 already fix the endpoint list, the error envelope and the status codes. DATABASE.md fixes the stored values. Where the request template differs, **the approved documents win**. Every difference is deliberate:

| Template asked for | What this API does | Authority |
|---|---|---|
| `{success, message, data, timestamp}` envelope | **Success responses are the bare resource JSON**; HTTP status carries success or failure. Errors use the ARCH envelope `{"error": {code, message, retryable, details, request_id}}`. Timestamps are fields of the resources (`created_at`, `generated_at`) and the standard `Date` header. A second envelope would conflict with the OpenAPI-generated TypeScript types and the frontend error handler | ARCH 6.2, 6.6, ADR-22 |
| `POST /calls/upload` | `POST /calls` | ARCH 6.2 |
| `POST /calls/{id}/process`, response with job ID | **Does not exist.** Analysis starts automatically when the upload is accepted (`202`). A manual retry uses `POST /calls/{id}/retry`. PRD 6.1 allows "or it starts automatically" | ARCH 3.3, 4.2, 6.4 |
| `GET /jobs/{job_id}` | **Does not exist.** There is no job table; the call is the job. Job status, stage, retry count, error and timestamps are fields of `GET /calls/{id}/status` | ARCH 6.4, ADR-07; DATABASE 2.1, 2.2 |
| `PATCH /calls/{id}/transcript` (manual correction) | **Not provided.** The PRD has no transcript editing, and the template allows it only if the PRD includes it. The transcript is read-only. Only speaker **roles** can be corrected (FR-S4) | PRD 3.2, FR-S4 |
| `GET /calls/{id}/speakers`, `PATCH /calls/{id}/speakers/{speaker_id}` | Speakers are returned inside `GET /calls/{id}/transcript`. Roles are corrected with one bulk `PUT /calls/{id}/speaker-roles`, because a role swap must change both speakers atomically (one rep per call) | ARCH 3.5, 6.2; DATABASE 2.4 |
| `GET /calls/{id}/evidence` | Evidence is part of `GET /calls/{id}/analysis` | ARCH 6.2 |
| `GET /calls/{id}/action-items`, `GET /action-items/{id}` | Action items are part of `GET /calls/{id}/analysis`. No per-item resource exists. Action items have no editable status in the MVP (V6 is V2) | ARCH 6.2; PRD V6; ADR-14 |
| Classification `INSUFFICIENT_EVIDENCE` | **`verdict` is `RED`, `GREEN` or `null`.** `null` means tone was not run. Thin evidence is reported as `confidence.level = "low"` plus `limited_evidence_reason`. It is never reported as GREEN without that qualification and never as a third verdict | PRD FR-T2, assumption 6; DATABASE 0 |
| Role values `SALES_REPRESENTATIVE`, `CUSTOMER`, `UNKNOWN` | `sales_rep`, `customer`, `unknown` (the stored values; the UI displays "Sales Rep" and "Customer") | DATABASE 2.4; DESIGN 13.3 |
| Optional call name on upload | Not supported. The display name is the sanitized filename and there is no rename | DESIGN 6 (no rename) |
| Date filters on `GET /calls` | Not supported (not in the approved query set) | ARCH 6.2 |
| Numeric `confidence`, action-item `confidence` and `status` | `confidence.level` (`high / medium / low`) with `factors`; action items carry `modality` and `owner_basis` instead | ADR-12, ADR-14 |
| Per-user ownership checks | Not applicable. No users or accounts | PRD 3.2, assumption 3; ADR-20 |

Section 19 lists the small additions this document proposes to the approved documents (two error codes and a few conventions).

## 1. API Overview

| Item | Specification |
|---|---|
| Purpose | Let one web client upload an `.m4a` call recording, follow asynchronous processing, read the transcript, speaker roles, RED/GREEN tone result with verified evidence and action items, manage analysis settings, and export or delete results |
| Backend framework | **FastAPI** (Python 3.12, Uvicorn, Pydantic v2), SQLAlchemy 2.0 over SQLite (WAL), as selected in ARCH 1.1 |
| Style | REST over HTTP, JSON bodies, resource-oriented paths, `snake_case` field names |
| Base URL | `/api/v1` on the **same origin** as the web app (the container serves both). Local example used below: `http://localhost:8000/api/v1` (the port is an example) |
| Versioning | Path prefix `/api/v1`. A breaking change introduces `/api/v2` and the old version stays until clients move. Adding optional response fields or new endpoints is not breaking. The OpenAPI document generated by FastAPI is the machine-readable contract (ADR-22) |
| Authentication | **None in the application** (PRD assumption 3, ADR-20). For a hosted demo an optional HTTP Basic gate protects all routes (section 11) |
| Request content types | `application/json` for all bodies, except `POST /calls`, which is `multipart/form-data` |
| Upload file types | Part content type `audio/mp4`, `audio/x-m4a` or `audio/m4a` (advisory; `application/octet-stream` tolerated), extension `.m4a`, and an MP4 `ftyp` signature (section 3) |
| Response content types | `application/json`, except export downloads (`application/json` or `text/markdown` as attachments) and `204` responses |
| Time format | ISO-8601 UTC with `Z`, for example `2026-11-23T09:14:05Z`. In-call positions are integer milliseconds (`start_ms`, `end_ms`) |
| Identifiers | UUID strings (DATABASE 2) |
| Long-running work | Asynchronous. Requests that start work return `202`; the client polls `GET /calls/{id}/status` every 2 seconds until a terminal status (ARCH 4.2) |
| Language | English transcripts only (PRD 3.2) |

## 2. Standard Response Structure

### 2.1 Success

A successful response is the resource itself, with no wrapper.

```
200 OK
Content-Type: application/json

{ ...resource fields... }
```

Lists use one shape everywhere:

```json
{ "items": [ ], "total": 42, "page": 1, "page_size": 20 }
```

### 2.2 Error

Every error, including unexpected ones, uses one envelope produced by a single handler (ARCH 6.6):

```json
{
  "error": {
    "code": "FILE_TOO_LARGE",
    "message": "File is 74.0 MB; the limit is 50 MB.",
    "retryable": false,
    "details": { "limit_mb": 50, "declared_mb": 74.0 },
    "request_id": "req_7f3a9c1e"
  }
}
```

| Field | Meaning |
|---|---|
| `code` | Stable machine-readable code from the catalog in section 14. Clients branch on this, never on `message` |
| `message` | What happened, what was not done, what the user can do (DESIGN 13.3). Safe to show |
| `retryable` | Whether repeating or retrying the same action can succeed |
| `details` | Small object with safe context (limits, field errors, the call status). Never stack traces, provider payloads, transcript text or secrets |
| `request_id` | Same value as the `X-Request-ID` response header and the server log lines for that request |

**Asynchronous failures are not HTTP errors.** If validation or transcription fails after the upload was accepted, the request that discovers it (`GET /calls/{id}/status`) succeeds with `200`, and the failure is reported in the `failure` object using the same codes. The HTTP error envelope is only for the request that was just made.

### 2.3 HTTP status codes

| Code | Used for |
|---|---|
| `200 OK` | Successful read, settings save, export |
| `202 Accepted` | Work started in the background: upload, retry, role correction |
| `204 No Content` | Successful delete |
| `401 Unauthorized` | Basic gate enabled and credentials missing or wrong (`WWW-Authenticate: Basic` header) |
| `404 Not Found` | Unknown or malformed `call_id`; unknown route |
| `409 Conflict` | Right request, wrong state: transcript or analysis not ready, call still processing, not retryable |
| `413 Content Too Large` | Upload exceeds the size cap |
| `415 Unsupported Media Type` | Wrong file type, or request is not `multipart/form-data` on upload |
| `422 Unprocessable Content` | Syntactically valid request with invalid content (empty file, invalid settings, invalid roles, bad query value) |
| `429 Too Many Requests` | Upload throttle (`Retry-After` header) |
| `500 Internal Server Error` | Unexpected failure, including database errors (`INTERNAL_ERROR`, no internals leaked) |
| `503 Service Unavailable` | Daily analysis cost cap reached; readiness failure |

## 3. Audio Upload and Call APIs

### 3.1 `POST /api/v1/calls` (API-01)

Uploads one `.m4a` recording, stores it, creates the call (`status = uploaded`) and queues analysis. Approved as `M1`, `M2`, FR-U1 to FR-U3, FR-U6.

**Request**

```
POST /api/v1/calls
Content-Type: multipart/form-data; boundary=...

--boundary
Content-Disposition: form-data; name="file"; filename="SYNTHETIC_demo_upload.m4a"
Content-Type: audio/mp4

<binary>
--boundary--
```

| Part | Required | Rules |
|---|---|---|
| `file` | yes | Exactly one file part, named `file` |
| any other part | no | Not accepted. Unknown parts are rejected, consistent with ARCH 6.3. There is no call-name field (section 0) |

**Synchronous validation** (cheap checks at the edge, ARCH 3.3; nothing paid is called):

| Check | Rule | Error |
|---|---|---|
| Request type | `multipart/form-data` | `415 REQUEST_INVALID` |
| File part present | `file` exists | `422 REQUEST_INVALID` |
| Single file | Not more than one file part | `422 TOO_MANY_FILES` |
| Size | Streamed to a temp file; aborted as soon as bytes exceed `MAX_UPLOAD_SIZE_MB` (default **50**); also rejected from a declared `Content-Length` | `413 FILE_TOO_LARGE` |
| Empty | Zero bytes | `422 FILE_EMPTY` |
| Extension | `.m4a`, case-insensitive | `415 INVALID_FILE_TYPE` |
| Declared type | `audio/mp4`, `audio/x-m4a`, `audio/m4a`; `application/octet-stream` tolerated | `415 INVALID_FILE_TYPE` |
| Container signature | Bytes 4-8 are `ftyp` and the major brand is in the allow list (`M4A `, `mp42`, `isom`, `M4B `, `mp41`, `iso2`). A renamed `.mp3` fails here | `415 INVALID_FILE_TYPE` |
| Rate | `RATE_LIMIT_UPLOADS_PER_HOUR` per IP (default 20) | `429 RATE_LIMITED` |
| Daily cap | `DAILY_ANALYSIS_LIMIT` per UTC day (default 50) | `503 DAILY_LIMIT_REACHED` |

**Asynchronous validation** (worker, stage `validation`, before any paid call): decodability, DRM or unreadable streams, duration 10 s to 30 min, silence. These failures appear in the status resource as `AUDIO_UNREADABLE`, `AUDIO_CORRUPTED`, `DURATION_OUT_OF_RANGE`, `AUDIO_SILENT`. The upload response therefore does not include a duration.

**Success: `202 Accepted`**

```
Location: /api/v1/calls/3b9e2c54-6f1a-4d8e-9a77-5c0d2e8b1f43
```

```json
{
  "id": "3b9e2c54-6f1a-4d8e-9a77-5c0d2e8b1f43",
  "status": "uploaded",
  "name": "SYNTHETIC_demo_upload.m4a",
  "size_bytes": 4718592,
  "created_at": "2026-11-23T09:14:05Z"
}
```

`name` is the sanitized display filename (control characters and path separators stripped, length capped). The stored audio key is a server UUID and is never returned.

**Duplicate submissions.** The same file uploaded twice creates two calls; no idempotency key is specified in the approved documents (section 19).

### 3.2 `GET /api/v1/calls` (API-02)

Paginated call history. Approved as `M11`, FR-D5. Parameters and limits are in section 13.

**Response `200`**

```json
{
  "items": [
    {
      "id": "bac8b72d-5aa1-54d3-b061-55501f86e604",
      "name": "SYNTHETIC_red_billing_dispute.m4a",
      "status": "complete",
      "status_group": "complete",
      "tone": "RED",
      "duration_ms": 59000,
      "size_bytes": 960000,
      "is_synthetic": true,
      "created_at": "2026-11-23T09:14:05Z"
    }
  ],
  "total": 1,
  "page": 1,
  "page_size": 20
}
```

| Field | Notes |
|---|---|
| `status` | Exact stored status: `uploaded, validating, transcribing, analyzing, complete, partial, failed` |
| `status_group` | `in_progress` (uploaded, validating, transcribing, analyzing), `complete`, `partial`, `failed`. Matches the History filter (DESIGN 13.2) |
| `tone` | The verdict of the **latest** analysis: `RED`, `GREEN`, or `null` (rendered "Not analyzed"). A partial call may have a verdict if tone completed |
| `duration_ms` | `null` until validation has read it |

### 3.3 `GET /api/v1/calls/{call_id}` (API-03)

Call metadata plus a summary of the latest analysis. Approved as `M10`, `M11`.

```json
{
  "id": "bac8b72d-5aa1-54d3-b061-55501f86e604",
  "name": "SYNTHETIC_red_billing_dispute.m4a",
  "status": "complete",
  "status_group": "complete",
  "size_bytes": 960000,
  "duration_ms": 59000,
  "audio_retained": false,
  "is_synthetic": true,
  "failure": null,
  "latest_analysis": {
    "run_number": 1,
    "status": "complete",
    "verdict": "RED",
    "confidence_level": "medium",
    "settings_version": 1,
    "created_at": "2026-11-23T09:15:42Z"
  },
  "created_at": "2026-11-23T09:14:05Z",
  "updated_at": "2026-11-23T09:15:42Z"
}
```

`audio_retained` is true while the stored file exists (`storage_key` not null). `latest_analysis` is `null` until one exists. `failure` is `null` or `{stage, code, message, retryable}`. No audio URL exists in any response (section 11).

### 3.4 `DELETE /api/v1/calls/{call_id}` (API-10)

Deletes the call and, by cascade, its transcript, utterances, speaker roles, analyses, evidence, action items and stage runs, then removes the audio file (DATABASE 7.3). Approved as FR-D6 and the PRD privacy requirement.

- `204 No Content` on success. Hard delete; there is no undo and no soft-deleted state.
- `409 CALL_IN_PROGRESS` while status is `uploaded`, `validating`, `transcribing` or `analyzing`.
- `404 CALL_NOT_FOUND` for an unknown ID (repeating a delete returns `404`).
- Provider-side deletion is attempted only where the provider supports it (ARCH 10.5). A failure there cannot be shown in a `204`; see section 19.

## 4. Processing APIs

### 4.1 Starting analysis (no endpoint)

`POST /calls` is the start. The worker atomically claims the call (`uploaded -> validating` with `locked_at`), so a call can never be processed twice, and the API process never runs pipeline work (ARCH 6.4). There is no `POST /calls/{id}/process`, no request body and no job ID: use the call `id` everywhere.

**Duplicate-processing prevention**

| Situation | Behavior |
|---|---|
| Two workers see the same `uploaded` call | One atomic update wins; the other claims nothing |
| `POST /calls/{id}/retry` while the call is processing | `409 NOT_RETRYABLE`, `details.reason = "IN_PROGRESS"` |
| `PUT /calls/{id}/speaker-roles` while processing | `409 CALL_IN_PROGRESS` |
| Restart mid-job | Startup recovery requeues or fails stale locked calls (`JOB_STALE_AFTER_SEC`, `JOB_MAX_ATTEMPTS`) |

### 4.2 `GET /api/v1/calls/{call_id}/status` (API-04)

The lightweight polling resource: overall status, the seven stage states with real messages and times, and failure information. Approved as `M10`, FR-D3. Each stage is reported from its `stage_runs` row, so a stage is `succeeded` only after it truly finished (ARCH 3.1).

```json
{
  "call_id": "3b9e2c54-6f1a-4d8e-9a77-5c0d2e8b1f43",
  "status": "transcribing",
  "status_group": "in_progress",
  "current_stage": "transcription",
  "completed_stages": 1,
  "total_stages": 7,
  "attempt_count": 1,
  "started_at": "2026-11-23T09:14:08Z",
  "completed_at": null,
  "failure": null,
  "partial_reason": null,
  "stages": [
    { "stage": "validation", "status": "succeeded", "attempt": 1,
      "started_at": "2026-11-23T09:14:08Z", "finished_at": "2026-11-23T09:14:19Z",
      "elapsed_ms": 11000, "message": "Audio is readable and within limits.", "error_code": null },
    { "stage": "transcription", "status": "running", "attempt": 1,
      "started_at": "2026-11-23T09:14:19Z", "finished_at": null,
      "elapsed_ms": 41000, "message": "Waiting for the transcription service.", "error_code": null },
    { "stage": "speaker_identification", "status": "pending", "attempt": null, "started_at": null, "finished_at": null, "elapsed_ms": null, "message": null, "error_code": null },
    { "stage": "tone_analysis", "status": "pending", "attempt": null, "started_at": null, "finished_at": null, "elapsed_ms": null, "message": null, "error_code": null },
    { "stage": "evidence_extraction", "status": "pending", "attempt": null, "started_at": null, "finished_at": null, "elapsed_ms": null, "message": null, "error_code": null },
    { "stage": "action_items", "status": "pending", "attempt": null, "started_at": null, "finished_at": null, "elapsed_ms": null, "message": null, "error_code": null },
    { "stage": "completion", "status": "pending", "attempt": null, "started_at": null, "finished_at": null, "elapsed_ms": null, "message": null, "error_code": null }
  ],
  "updated_at": "2026-11-23T09:14:48Z"
}
```

| Field | Rules |
|---|---|
| `status` / `status_group` | As in section 3.2. Terminal statuses: `complete`, `partial`, `failed` |
| `current_stage` | The stage whose latest run is `running`; `null` when terminal or not yet claimed |
| Progress | **Only stage counts are reported** (`completed_stages` of 7), because they are facts. There is **no percentage and no time estimate**, since neither is reliably known (STT turnaround varies) |
| Stage `status` | `pending` (no `stage_runs` row yet), `running`, `succeeded`, `failed`, `skipped` |
| `message`, `error_code` | From the stage's `result_summary` and `error_code`. Counts and timings only; no transcript text |
| `attempt_count` | `calls.attempt_count`, the recovery requeue count |
| `started_at` / `completed_at` | First stage start of the current run; `finished_at` of the `completion` stage, `null` until then |
| `failure` | `null`, or `{stage, code, message, retryable}` using codes from section 14. Present for `failed`, and for `partial` when a stage failed |
| `partial_reason` | Reason from the latest analysis, for example `ROLES_UNRESOLVED`, `TONE_FAILED`, `EXPLANATION_FAILED`, `ACTION_ITEMS_FAILED`; otherwise `null` |
| Re-runs | When roles are corrected or a stage is retried, each stage reports its **latest** attempt; stages 1-3 keep their original runs |

The response is cheap (one call row plus at most seven stage rows) and is not cached. It carries no transcript or analysis content.

### 4.3 `POST /api/v1/calls/{call_id}/retry` (API-07)

Retries from a named stage using stored artifacts; no re-upload, and transcription is not repeated unless it is the named stage. Approved as `M10`, FR-E3, FR-E5, FR-S6.

**Request**

```json
{ "stage": "transcription" }
```

| `stage` | Allowed when |
|---|---|
| `validation` | status `failed` |
| `transcription` | status `failed` and `failure_stage` is `transcription` (or `validation` already passed) |
| `speaker_identification`, `tone_analysis`, `evidence_extraction`, `action_items` | status `partial` (a transcript exists). The pipeline resumes at the named stage and writes a **new analysis run**; earlier runs are kept (ARCH 3.5) |

`completion` is never retryable. Any other combination returns `409 NOT_RETRYABLE` with `details.reason` set to one of `IN_PROGRESS`, `STAGE_NOT_RETRYABLE`, or `AUDIO_NOT_RETAINED` (transcription retry after the audio was removed by retention: re-upload instead).

**Success: `202`**

```json
{ "call_id": "7d1c4a90-2b5e-4f36-8c19-a0e6d3b7f852", "status": "transcribing" }
```

The returned `status` is the call's new status. Retries consume the daily analysis cap (inferred from ARCH 11 "analyses started"; section 19).

## 5. Transcription API

### 5.1 `GET /api/v1/calls/{call_id}/transcript` (API-05)

The transcript, its provenance, and the speaker roles. Approved as `M3`, `M4`, FR-S1, FR-S2.

```json
{
  "call_id": "...",
  "status": "completed",
  "provider": "assemblyai",
  "model": null,
  "language": "en",
  "speaker_count": 2,
  "speakers": [
    { "speaker_label": "A", "role": "customer",  "source": "auto", "status": "confident", "level": "high" },
    { "speaker_label": "B", "role": "sales_rep", "source": "auto", "status": "confident", "level": "high" }
  ],
  "utterances": [
    { "id": "...", "idx": 0, "speaker_label": "A", "role": "customer",
      "start_ms": 0, "end_ms": 7000, "text": "...",
      "asr_confidence": null, "speaker_confidence": null, "low_attribution": false }
  ]
}
```

- `utterances` are ordered by `idx`. Their text is the verbatim, auto-generated transcript ("From the transcript" in the UI). `role` is resolved from `speakers` by label.
- `speakers[].status` is `unresolved | uncertain | confident | confirmed`; `source` is `auto` or `user`; `level` is `high | medium | low` or `null`. **The first speaker is never assumed to be the sales rep** (ARCH 3.5): an `unresolved` speaker has role `unknown`.
- If diarization produced one speaker, `speaker_count` is 1, the speaker is `unknown / unresolved`, and the client shows an unlabeled transcript with a warning (FR-S5). No attribution is invented.
- `asr_confidence` and `speaker_confidence` are `null` when the provider did not return them.
- Never returned: `raw_response`, provider job ID, storage key.

`404 CALL_NOT_FOUND`; `409 TRANSCRIPT_NOT_READY` (transcript not `completed`, including failed transcription). The response is sent with `Cache-Control: no-store`.

### 5.2 Manual transcript correction: not provided

`PATCH /calls/{id}/transcript` is **not part of the API**. The PRD includes no manual transcript editing, and DATABASE.md makes `utterances` immutable (an update trigger rejects changes). This also protects the core guarantee: every quote stays a literal span of the stored transcript. The only user correction is speaker roles (section 6).

## 6. Speaker Identification API

### 6.1 Reading speakers

Part of `GET /calls/{id}/transcript` (section 5.1). There is no separate speakers endpoint.

### 6.2 `PUT /api/v1/calls/{call_id}/speaker-roles` (API-08)

Confirms or corrects which speaker is the sales rep, then re-runs stages 4-7 on the stored transcript with the **current** saved settings. No re-upload and no re-transcription. Approved as `M4`, FR-S4, DESIGN roles modal.

**Request**

```json
{ "roles": { "A": "customer", "B": "sales_rep" } }
```

| Rule | Error |
|---|---|
| Keys must be exactly the call's speaker labels | `422 INVALID_ROLES` |
| Values are `sales_rep`, `customer` or `unknown` | `422 INVALID_ROLES` |
| Exactly one `sales_rep` (the database allows at most one per call; the service requires one because the purpose is to evaluate the rep) | `422 INVALID_ROLES` |
| Call must have a completed transcript | `409 TRANSCRIPT_NOT_READY` |
| Call must not be processing | `409 CALL_IN_PROGRESS` |

**Effect:** each submitted speaker is stored with `source = user`, `status = confirmed`, `level = high`; the call moves to `analyzing`; a **new analysis run** is created (the previous run is kept for audit). The old verdict stays readable until the new run completes; the latest analysis is shown once it exists.

**Success: `202`**

```json
{ "call_id": "bac8b72d-5aa1-54d3-b061-55501f86e604", "status": "analyzing" }
```

## 7. Tone Analysis API

### 7.1 `GET /api/v1/calls/{call_id}/analysis` (API-06)

The latest analysis: verdict, confidence, explanation, evidence, action items and the settings snapshot, returned together so the UI can show "From the transcript" and "AI interpretation" side by side (ARCH 8.4). Approved as `M5` to `M9`, `M13`.

| Field | Meaning and rules |
|---|---|
| `analysis_id`, `run_number` | Latest run. Earlier runs are kept in the database but not exposed in the MVP |
| `status` | `complete` or `partial` |
| `partial_reason` | Required when `partial`. For example `ROLES_UNRESOLVED` (tone not run) |
| `verdict` | `RED`, `GREEN` or `null`. `null` means tone was **not** evaluated and must be shown as "Not analyzed" |
| `confidence` | `{level, factors}` or `null` when `verdict` is `null`. `level` is `high / medium / low`. `factors` are the visible reasons (role confidence, rep speech seconds, evidence strength, dropped evidence). Never a percentage |
| `limited_evidence_reason` | Specific text for the limited-evidence banner, or `null`. Set when confidence is low, rep speech is short, or roles are uncertain. A low-confidence GREEN is a **GREEN with this note**, not a verdict of insufficient evidence |
| `explanation` | "AI interpretation". `null` only if the explanation call failed; never a placeholder. A GREEN explanation says only that no behavior matching the enabled criteria was found |
| `rep_speaker` | `{speaker_label, role_source}`: the speaker evaluated as the rep **in this run**, and whether roles were `auto` or `user` confirmed. `null` when tone was not run |
| `evidence[]` | Verified evidence (below). Empty for GREEN. A RED always has at least one |
| `action_items[]` | Verified action items (section 8). May be empty (client shows "No action items identified") |
| `dropped_evidence` | `{count, reasons}`: how many findings failed verification and a tally by reason code (`QUOTE_NOT_FOUND`, `NOT_REP_UTTERANCE`, ...). The unverified text itself is never returned |
| `settings` | `{version, is_current, sensitivity, config}`: the snapshot used for **this** analysis. `is_current` is false if newer settings exist (drives "Differs from current settings") |
| `generated_by` | `{model, prompt_version}` |

**Evidence item**

| Field | Meaning |
|---|---|
| `id`, `ref` | UUID and short reference (`E1`). The explanation cites refs |
| `utterance_id`, `utterance_idx` | The transcript segment. Always a real utterance of this call |
| `speaker_label` | Always the evaluated rep's label (database-enforced) |
| `start_ms` | Taken from the utterance, never from the model |
| `quote`, `char_start`, `char_end` | The verbatim span copied from the utterance. `text.substring(char_start, char_end) === quote` (0-based, end exclusive) |
| `criterion_id`, `criterion_label` | The matched negative-tone criterion, for example `dismissive`, `rude`, `hostile`, or a custom criterion |
| `severity` | 1 mild, 2 clear, 3 severe |
| `rationale` | "AI interpretation" of why the quote matches the criterion |

**Errors:** `404 CALL_NOT_FOUND`; `409 ANALYSIS_NOT_READY` (no analysis yet, or the call failed before one was written; `details.call_status` says which). Sent with `Cache-Control: no-store`.

### 7.2 Evidence endpoint: not provided

`GET /calls/{id}/evidence` is not a separate endpoint; `evidence[]` above is the evidence list and every item references an actual transcript segment through `utterance_id`.

## 8. Action Item API

Action items are returned in `action_items[]` of `GET /calls/{id}/analysis` (section 7). There are no separate action-item endpoints (section 0).

| Field | Meaning and rules |
|---|---|
| `id`, `ref` | UUID, short reference (`A1`) |
| `type` | `commitment`, `follow_up`, `information_promised`, `customer_task` |
| `task` | "AI summary" wording. Always shown next to the quote |
| `modality` | `definite` or `tentative`. Conditional, hypothetical and question statements are never stored. `tentative` appears only if the settings allow it |
| `owner_text`, `owner_basis` | `owner_text` is `null` when `owner_basis` is `none`: **no owner is invented**. `owner_basis` is `explicit_name`, `explicit_role`, `committing_speaker` (the server writes the speaker's role label) or `none`. The client displays `null` as "Not specified" |
| `deadline_text` | `null` unless a deadline was stated in the quote. Returned exactly as spoken ("by Friday"), never converted to a calendar date |
| `utterance_id`, `utterance_idx`, `speaker_label`, `start_ms` | Where it was said and by whom |
| `quote`, `char_start`, `char_end` | Supporting verbatim span; always present (an action item cannot exist without it) |

There is no editable `status` and no `confidence` on action items in the MVP (ARCH ADR-14; PRD V6 is V2). `GET /action-items/{id}` is not provided.

The dashboard summary (section 10) also lists recent action items across calls.

## 9. Analysis Settings APIs

One global settings profile, stored as an append-only history (DATABASE 2.6). The current settings are the highest version.

### 9.1 `GET /api/v1/settings` (API-12)

```json
{
  "version": 1,
  "source": "default",
  "created_at": "2026-11-23T08:00:00Z",
  "config": { "tone": { ... }, "actions": { ... } }
}
```

`config` is the settings document below. `created_at` is the last-saved time. Approved as `M12`, FR-C1, FR-C2.

### 9.2 `PUT /api/v1/settings` (API-13)

Validates the full document and saves it as a **new version**. Approved as `M12`, `M13`, FR-C1 to FR-C5.

**Request schema** (defaults in ARCH 9.1)

| Path | Type and rules |
|---|---|
| `tone.criteria[]` | List of `{id, label, enabled, custom}`; at least one criterion enabled |
| `tone.criteria[].id` | Built-in ids `rude`, `hostile`, `dismissive` must all be present with `custom: false`. For a new custom criterion the client **omits** `id`; the server assigns a stable one |
| `tone.criteria[].description` | Returned by `GET`. Server-derived (built-in text is fixed; for a custom criterion it equals `label`). Accepted and ignored on write, so a client can send back exactly what it read |
| `tone.criteria[].label` | Custom: 1-140 characters of plain text, unique (case-insensitive) among criteria. Built-in labels are server-defined |
| custom criteria | At most 5 |
| `tone.sensitivity` | `low`, `medium` or `high` |
| `tone.guidance` | String, at most 500 characters, may be empty |
| `actions.types` | Booleans `commitments`, `follow_ups`, `information_promised`, `customer_tasks`; at least one `true` |
| `actions.include_tentative` | Boolean |
| `actions.owner_rule` | `explicit_or_committing_speaker` or `explicit_only` |
| `actions.capture_relative_deadlines` | Boolean |
| `actions.guidance` | String, at most 500 characters, may be empty |
| unknown fields | Rejected |

Control characters are stripped from all text. Length limits also mitigate prompt injection and cost abuse (FR-C5). Free text is never written to logs.

**Success `200`:** the same shape as `GET /settings`, with the new `version`.

**Error `422 SETTINGS_INVALID`:** per-field errors so the UI can show them inline.

```json
{
  "error": {
    "code": "SETTINGS_INVALID",
    "message": "Settings were not saved. Fix the highlighted fields and try again.",
    "retryable": false,
    "details": { "fields": [
      { "path": "tone.criteria", "message": "Enable at least one tone criterion." },
      { "path": "tone.guidance", "message": "Must be 500 characters or fewer." }
    ] },
    "request_id": "req_2d84b0aa"
  }
}
```

**Versioning and history.** Every save inserts a new `settings_versions` row (it is never updated). Each analysis stores the version it used, so changing settings does **not** modify any past result. Settings apply to **subsequent** analyses; the UI states that past results are unchanged (PRD 6.8). Concurrent saves are last-write-wins; the later insert becomes current and both remain in history.

### 9.3 `POST /api/v1/settings/reset` (API-14)

Saves the defaults as a new version with `source = "reset"` and returns it (same shape as `GET /settings`). No request body. Approved as FR-C6 and PRD 6.8 step 5. History is kept.

## 11. Authentication and Authorization

The PRD requires **no login, accounts or roles** (PRD 3.2, assumptions 3 and 7). The architecture adds only an optional deployment gate (ARCH 10.3, ADR-20).

| Aspect | Specification |
|---|---|
| Application authentication | None |
| Optional gate | If `BASIC_AUTH_USER` and `BASIC_AUTH_PASSWORD` are both set, **every route** requires `Authorization: Basic ...`. Failure returns `401` with `WWW-Authenticate: Basic`. Browsers prompt natively, so the UI needs no login screen |
| Authorization model | One trust domain. Anyone who passes the gate may use every endpoint. There are no roles, owners or per-call permissions |
| Resource ownership checks | **Not applicable**: calls, settings and results have no owner (DATABASE 7.1). The API does not claim per-user isolation |
| Audio protection | There is **no endpoint that returns audio**, no download route and no endpoint that accepts a URL (ARCH 6.2, ADR-18). The storage key is never returned |
| Transcript and analysis protection | Readable only through the endpoints in this document, behind the gate when enabled; `Cache-Control: no-store`; never logged; deleted with the call |
| Provider data | No endpoint returns provider keys or raw provider payloads |

Per-endpoint access:

| ID | Endpoint | Authentication | Authorized user | Ownership check | Access restrictions |
|---|---|---|---|---|---|
| API-01 | `POST /calls` | None (optional Basic gate) | Any caller that passes the gate | None (no owners) | Upload throttle per IP; daily cap; size and type checks |
| API-02 | `GET /calls` | None (optional Basic gate) | Any caller that passes the gate | None (no owners) | None beyond the gate |
| API-03 | `GET /calls/{call_id}` | None (optional Basic gate) | Any caller that passes the gate | None (no owners) | None beyond the gate |

## 13. Pagination, Filtering and Sorting

Applies to `GET /api/v1/calls` (API-02). Parameters not listed here are rejected with `422 REQUEST_INVALID`.

| Parameter | Type | Default | Rules |
|---|---|---|---|
| `page` | integer | `1` | 1 or greater. A page beyond the last returns `200` with empty `items` |
| `page_size` | integer | `20` | 1 to **100** (maximum). Larger values return `422`, they are not silently capped |
| `q` | string | none | Case-insensitive substring match on the call name. Maximum 100 characters; `%`, `_` and `\` are escaped and the value is a bound parameter. Parity with the UI search "Search by call name" |
| `tone` | `red`, `green`, `none` | none | Filters on the verdict of the latest analysis. `none` means no verdict (not analyzed, failed, or tone not run) |
| `status` | `in_progress`, `complete`, `partial`, `failed` | none | `in_progress` covers `uploaded`, `validating`, `transcribing`, `analyzing` |
| `sort` | `newest`, `oldest` | `newest` | By `created_at` (upload time) |

Not supported: date-range filters, other sort fields, filtering by exact status such as `transcribing`. They are not in the approved query set; adding them later is non-breaking.

Filters combine with AND. `total` is the count after filtering. Ordering is stable: ties on `created_at` are broken by `id`. The History view polls every 5 seconds while any call is in progress (DESIGN).

| Transcription failure | Status `failure` | 200 | `STT_PROVIDER_ERROR`, `STT_TIMEOUT`, `STT_UNSUPPORTED_AUDIO`, `STT_EMPTY_TRANSCRIPT` | yes except unsupported or empty | Call `failed`; no transcript is fabricated; retry available |
| Diarization failure | Status `failure` / `partial_reason` | 200 | `DIARIZATION_UNAVAILABLE` | no | Transcript shown unlabeled; tone not run |
| Speaker attribution uncertainty | `speakers[].status`, `confidence`, `limited_evidence_reason` | 200 | (not an error) `ROLES_UNRESOLVED` as `partial_reason` when unresolved | n/a | Uncertain roles force Low confidence; unresolved roles skip tone |
| AI provider unavailable | Status `failure` | 200 | `LLM_UNAVAILABLE`, `LLM_RATE_LIMITED` | yes | Call `partial`, transcript kept |
| Invalid AI response | Status `failure` | 200 | `LLM_INVALID_OUTPUT` | yes | One repair retry already used; no fallback text |
| Insufficient transcript evidence | Analysis | 200 | (not an error) `limited_evidence_reason`, `confidence.level = low`; `ANALYSIS_EVIDENCE_UNVERIFIED` when quotes were dropped | n/a | Verdict stays RED or GREEN; never a third value |
| Action-item extraction failure | Analysis | 200 | `partial_reason = ACTION_ITEMS_FAILED` with the stage's `LLM_*` code | yes | Tone result kept |
| Invalid settings | `PUT /settings` | 422 | `SETTINGS_INVALID` | no | `details.fields[]` |
| Invalid roles | `PUT speaker-roles` | 422 | `INVALID_ROLES` | no | |
| Invalid request (query, body, form) | Any | 422 (415 for wrong content type) | `REQUEST_INVALID` (proposed) | no | `details.fields[]` |
| Unauthorized | Any, gate enabled | 401 | `UNAUTHORIZED` (proposed) | no | May come from the gate before the application, with only `WWW-Authenticate` |
| Resource not found | Call routes | 404 | `CALL_NOT_FOUND` | no | Malformed IDs also return 404, so the response does not reveal ID formats |
| Transcript or analysis not ready | Read routes | 409 | `TRANSCRIPT_NOT_READY`, `ANALYSIS_NOT_READY` | yes (poll status) | `details.call_status` |
| Call still processing | Delete, role change | 409 | `CALL_IN_PROGRESS` | yes | |
| Cannot retry | Retry | 409 | `NOT_RETRYABLE` | no | `details.reason` |
| Job interrupted by restart | Status `failure` | 200 | `JOB_INTERRUPTED` | yes | |
| Database error | Any | 500 | `INTERNAL_ERROR` | maybe | Message is generic; the cause is logged with the `request_id` |
| Rate limit exceeded | Upload | 429 | `RATE_LIMITED` | yes | `Retry-After` header |
| Daily cost cap | Upload, retry, role change | 503 | `DAILY_LIMIT_REACHED` | yes (next UTC day) | |
| Anything unexpected | Any | 500 | `INTERNAL_ERROR` | maybe | |

**Safe error content.** Messages are written from the code catalog, not copied from exceptions or providers. `details` may hold limits, field paths, statuses and reason codes only. Never included: API keys, credentials, stack traces, SQL, file system paths, raw provider responses, transcript text, or settings free-text. A provider's own error text is logged (without transcript content) and replaced in the response by the mapped message.

## 15. API Security

| Area | Rule |
|---|---|
| Input validation | Every body, query string and response is a Pydantic v2 model; unknown fields rejected on writes; enums closed; strings length-capped; control characters stripped from text; `call_id` validated as a UUID before use |
| File upload security | Two layers (ARCH 10.1, 10.2): streaming edge checks (size, extension, type, `ftyp` signature) then worker checks (probe, full decode, duration, silence). Files are stored under a server-generated UUID in a private directory (`0700` / `0600`) outside any served path. User filenames are display metadata only. FFmpeg runs without a shell, with timeouts and a local-file-only protocol list. Files are never "repaired" |
| Request size limits | 50 MB file cap enforced while streaming (and from `Content-Length`); JSON bodies are small (settings at most a few KB). Normal routes have a short request timeout; the upload route allows time for the body only |
| Rate limiting | `RATE_LIMIT_UPLOADS_PER_HOUR` per IP on upload (429), `DAILY_ANALYSIS_LIMIT` as a cost cap (503). Other routes have no application-level throttle in the MVP (PRD asks for "basic" limiting); a hosted platform may add one |
| Authentication and authorization | None in the application; optional Basic gate (section 11) |
| Secure error messages | Section 14 |
| CORS | Same origin by default, so no CORS headers are sent. `CORS_ORIGINS` is an explicit allow list for local Vite development or a split deployment; never `*` |
| Transport | HTTPS only in hosted use (platform terminates TLS). Outbound calls use fixed provider base URLs with certificate verification and timeouts; no user-supplied URLs, so no SSRF surface |
| Response headers | Restrictive Content-Security-Policy and standard security headers; `Cache-Control: no-store` on transcript, analysis and export. All text is returned as JSON strings and must be rendered as text by clients |
| Secret management | Provider keys live only in server environment variables or the host secret store, loaded as `SecretStr`. They never appear in responses, OpenAPI examples, logs, exports or error messages |
| Safe logging | Structured logs carry `request_id`, `call_id`, `stage`, `error_code`, durations and token or audio-second counts. **Never logged:** keys, `Authorization` headers, transcript or audio content, settings free-text, upload filenames. `LOG_PROMPTS` is off by default and forbidden in hosted demos (ARCH 6.7) |
| Resource ownership validation | Not applicable in the MVP (no owners). Every call route still verifies that the call exists, and state-changing routes verify the call is in a permitted status |
| Prompt injection | Settings text and transcript text reach the model only inside delimited data blocks; model output is validated and verified before storage (ARCH 8.2). Settings length limits apply at the API |
| Data minimization | Exports are generated on demand and not stored; deleted calls leave no rows (DATABASE 7.3) |

## 18. API Design Decisions

| Topic | Decision | Reason | Alternatives | Trade-offs |
|---|---|---|---|---|
| REST conventions | Nouns for resources, plural collection (`/calls`), `snake_case`, IDs in the path, filters in the query, `PUT` for full settings replace, `POST` for actions that start work (`retry`) | Simple, predictable, matches ARCH 6.2 | RPC-style verbs; GraphQL | `speaker-roles` as one `PUT` is less granular than per-speaker `PATCH` but keeps the one-rep rule atomic |
| Endpoint set | The 15 endpoints of ARCH 6.2; template extras not added | "No unsupported features"; every endpoint maps to a requirement | Add convenience sub-resources (`/evidence`, `/speakers`) | Clients fetch one larger analysis payload instead of several small ones; fewer round trips and no inconsistent partial reads |
| Success format | Bare resource | HTTP status already signals success; types are generated from OpenAPI | `{success, message, data, timestamp}` envelope | Not the template's example; clients cannot rely on a `success` flag |
| Error format | One envelope with stable `code`, `retryable`, `details`, `request_id` | Frontend maps codes to copy; support can find the log line | Problem Details (RFC 9457) | Custom, but already approved |
| Status codes | `202` for background work, `204` for delete, `409` for state conflicts, `422` for semantic validation, `413` / `415` for upload checks, `503` for the daily cap | Distinguish "wrong input" from "wrong moment" | `400` for everything; `200` with error flags | Clients must handle more codes |
| Background processing | `202` plus polling of `GET /status` every 2 s; DB-backed in-process worker; the call row is the job | Simplest reliable approach for one service; survives restarts via recovery | Webhooks, WebSockets/SSE, Celery | Slight latency and request volume; no push. SSE is the documented upgrade (ADR-23) |
| Async failures | Reported in the status resource, not as HTTP errors | The request that reads the status succeeded | `4xx/5xx` on status reads | A client must inspect `failure` |
| Verdict values | `RED`, `GREEN`, `null` | PRD binary verdict; honest "Not analyzed" | Third value `INSUFFICIENT_EVIDENCE` | Clients must handle `null` and the limited-evidence note |
| Evidence integrity in the contract | Return `quote` with offsets and `utterance_id`; server values only | Client can verify; no model-supplied timestamps | Return quote only | Larger payload |
| Pagination | `page` / `page_size` (default 20, max 100), `total` returned | Matches the History table with page numbers; small data volume | Cursor pagination | Offset pages can shift while new calls arrive (acceptable for a single-user tool) |
| Versioning | URL prefix `/api/v1` | Visible, simple, cacheable | Header or media-type versioning | A new major version duplicates routes |
| Authentication | None; optional Basic gate | PRD requires none; protects API credits of a hosted demo | Full login/JWT | **Security trade-off:** one shared credential and no per-user isolation. Acceptable only for a single-user or demo deployment with synthetic or consented recordings |
| Audio access | No audio endpoint | Least exposure; player is V2 | Pre-signed URLs | Reviewers cannot replay audio in the app |
| Settings change safety | Append-only versions; analyses reference the version used | Historical results never change silently | Mutable settings row | `is_current` must be computed on read |
| Idempotency | None specified | Out of approved scope | `Idempotency-Key` on upload | Double-click or retry of an upload can create duplicate calls (the UI disables the button during upload) |

## 19. Assumptions and Open Items

These are inferences or small additions this document makes. Each needs a decision when ARCHITECTURE.md is next updated.

| # | Item | Proposal |
|---|---|---|
| 1 | Error catalog lacks codes for generic request validation and for the gate | Add `REQUEST_INVALID` (422, or 415 for a wrong upload content type) and `UNAUTHORIZED` (401) to ARCH 6.6 |
| 2 | `X-Request-ID` response header | Echo the envelope's `request_id` as a header (convention, no new data) |
| 3 | `status_group` and `in_progress` mapping | Derived from DESIGN 13.2 and the History filter; `uploaded` is grouped under `in_progress` |
| 4 | Retry stage rules (section 4.3) | Derived from the ARCH 3.2 state machine; the exact allowed stage list should be confirmed in the pipeline design |
| 5 | Role correction needs exactly one `sales_rep` | The database allows at most one; the service requires exactly one for the call to be evaluable. Revisit if "no rep" should be a valid user choice |
| 6 | Custom criterion id and label rules | The server assigns custom ids; the single user-entered text (1-140 chars, DESIGN 6F) is the label. Built-in labels fixed server-side |
| 7 | Retry and role correction count toward `DAILY_ANALYSIS_LIMIT` | Inferred from "analyses started per UTC day" (ARCH 11) |
| 8 | Delete cannot report a failed provider-side deletion in a `204` | If provider deletion is verified on Day 0 (ARCH Appendix A), change the response to `200 {"deleted": true, "warnings": [...]}` |
| 9 | Health endpoint behind the gate | ARCH says all routes require Basic when enabled. A hosting platform's health probe then needs credentials, or `/health` must be exempt. Decide at deploy time. Readiness also fails when no `settings_versions` row exists (DATABASE 9.2) |
| 10 | No idempotency key | Duplicate uploads create duplicate calls |
| 11 | Total calls in dashboard KPIs | `total_calls` is added as a plain count; ARCH lists the other KPIs |
