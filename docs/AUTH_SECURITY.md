# AUTH_SECURITY.md — Authentication, Authorization, and Security

> Scope: Local-first ScaleWorks AI assessment MVP. Follow `PRD.md` and `ARCHITECTURE.md` if they specify a different access model.

## 1. Security objectives

Protect:
- Uploaded audio recordings.
- Transcripts and speaker labels.
- Tone analysis and evidence.
- Action items.
- Local model credentials and configuration.
- Database integrity.

The assessment permits a local demonstration. Do not add complex multi-tenant authentication unless it is an approved product requirement. For a single-user local MVP, bind the backend to localhost and document that it is not an internet-facing deployment.

## 2. Authentication decision

### MVP
If the PRD does not require user accounts:
- Do not implement fake login screens.
- Run the application locally on `127.0.0.1`.
- Restrict access to the local machine.
- Keep the design modular so authentication can be added later.

### If authentication is required
Use a well-maintained password-hashing library and a server-side session or a carefully implemented token design. Do not write custom cryptography.

Requirements:
- Hash passwords with Argon2id or another approved modern password-hashing algorithm.
- Never store plaintext passwords.
- Use generic login failure messages.
- Rate-limit login and password-reset endpoints.
- Require strong secrets from environment variables.
- Expire sessions and support logout.
- Do not store long-lived bearer tokens in browser local storage if an HttpOnly secure cookie design is available and appropriate.

## 3. Authorization and resource ownership

If multiple users are introduced:
- Every call must have an owner or explicit access-control relationship.
- Check ownership on every call, transcript, evidence, action-item, and audio endpoint.
- Do not rely on a frontend-hidden button as authorization.
- Deny access by default.
- Return 404 or 403 according to the documented resource-disclosure policy.
- Admin privileges must be explicit and tested.

For local single-user mode, do not claim multi-user isolation.

## 4. Audio upload security

- Allow only approved audio formats; MVP accepts `.m4a`.
- Check extension, MIME type, file signature where practical, and successful media probing.
- Enforce a configurable maximum file size and duration.
- Generate a random server-side storage filename.
- Treat the original filename as untrusted display metadata.
- Prevent path traversal and directory escape.
- Store uploads outside the public frontend directory.
- Never execute uploaded content.
- Use FFmpeg/FFprobe with safely constructed argument arrays; avoid shell interpolation.
- Set processing timeouts and resource limits.
- Do not log audio bytes or full sensitive transcripts.

## 5. Secrets and environment

- Store secrets only in `.env` or a secret manager for a future deployment.
- Commit `.env.example`, never `.env`.
- Keep Hugging Face token read-only and least-privileged where supported.
- Do not expose tokens to React or browser bundles.
- Never return environment variables from API endpoints.
- Redact tokens from logs and exception messages.
- Rotate a token if it is accidentally exposed.

## 6. API security

- Validate request bodies with Pydantic schemas.
- Set upload size limits at application and server layers.
- Apply rate limits if exposed beyond localhost.
- Configure CORS for the exact development frontend origin; do not use wildcard origins with credentials.
- Use HTTPS for any non-local deployment.
- Keep error responses generic; detailed stack traces belong only in protected development logs.
- Use parameterized database operations and ORM query APIs.
- Protect state-changing routes against CSRF if cookie-based authentication is used.
- Keep dependencies updated and review advisories.

## 7. AI-specific safeguards

- Treat transcripts and audio-derived text as untrusted input.
- Do not let transcript content override system instructions or request secrets.
- Use fixed server-side prompts and strict output schemas.
- Do not execute commands, SQL, or tool calls generated by the model.
- Validate all model output before database writes.
- Require evidence references to resolve to real transcript segments.
- Do not classify customer speech as representative speech.
- Do not assume speaker order determines role.
- Preserve `UNKNOWN` speaker role and `INSUFFICIENT_EVIDENCE` when appropriate.
- Never invent action-item owners or deadlines.
- Do not present model confidence unless the implementation defines a meaningful, validated measure.

## 8. Privacy and retention

- Use only consented or synthetic recordings for the assessment.
- Explain where audio is stored.
- Restrict filesystem permissions where possible.
- Provide a delete-call operation that removes or schedules deletion of audio and associated analysis according to the retention policy.
- Avoid sending audio or transcripts to external services. The selected AI inference stack is local.
- Note that model downloads and Hugging Face gated-model access require internet access, but inference should remain local.
- Keep backups protected and delete them according to the same retention policy.

## 9. Logging and monitoring

Log:
- Request ID.
- Call/job ID.
- Processing stage.
- Duration and status.
- Sanitized error category.

Do not log:
- API tokens.
- Passwords.
- Full audio content.
- Unnecessarily complete transcripts.
- Sensitive customer details.

## 10. Security test checklist

- [ ] `.env` is ignored by Git.
- [ ] Hugging Face token is never sent to frontend.
- [ ] Invalid file types are rejected.
- [ ] Oversized files are rejected.
- [ ] Path traversal filenames cannot escape storage.
- [ ] Audio is not publicly served from the frontend directory.
- [ ] Unauthorized resource access is denied if accounts exist.
- [ ] Model output is schema-validated.
- [ ] Evidence must map to stored transcript segments.
- [ ] Errors do not expose secrets or stack traces to users.
- [ ] Deletion removes the intended records and files.
- [ ] CORS is restricted to approved origins.

## 11. Known limitations

A localhost-only MVP is not production-ready for multiple remote users. Before public deployment, add authentication, TLS, hardened storage, rate limiting, operational monitoring, backups, and a documented privacy/retention process. Do not claim these controls exist until implemented and tested.
